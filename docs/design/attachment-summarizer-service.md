### 技术设计文档：Attachment Summarizer Service

**版本：** 1.1
**日期：** 2023-10-27
**状态：** 草案，待评审

#### 1. 概述与目标

本服务旨在解决用户在处理大量邮件、文档附件时效率低下的痛点。核心目标是为用户提供一个轻量级、可嵌入现有工作流的微服务，能够自动提取并总结各种常见格式附件（PDF、Word、Excel、纯文本、图片中的文字）的核心内容。

**核心价值主张：** 将用户从“打开-阅读-理解-记录”的繁琐流程中解放出来，转变为“上传/引用-获取摘要-决策”的高效模式。该服务不追求生成完美的文学性总结，而是侧重于提取关键事实、数据、行动项和结论。

#### 2. 系统架构与核心组件

采用无状态微服务架构，便于水平扩展和独立部署。

-   **API 网关层 (API Gateway):** 负责接收外部请求，进行身份验证（API Key）、速率限制、请求日志记录。
-   **任务调度器 (Task Scheduler):** 接收来自网关的总结请求，将其转化为异步任务。这允许服务处理大文件而不会阻塞客户端。使用消息队列（如 Redis Streams 或 RabbitMQ）进行任务缓冲。
+   **文件处理器集群 (File Processor Workers):** 无状态工作节点，从任务队列中拉取任务。每个节点负责：
    *   **文件下载与解析 (File Fetcher & Parser):** 从提供的URL或直接上传的二进制流中下载文件。根据文件扩展名调用不同的解析器。
    *   **文本提取器 (Text Extractor):** 将解析后的数据结构（如PDF页面、Word段落、Excel单元格）转换为纯文本字符串。
    *   **摘要引擎 (Summarization Engine):** 核心模块，负责对提取的文本进行总结。
+   **结果存储 (Result Store):** 使用键值存储（如Redis）或对象存储（如S3）来保存摘要结果。`task_id` 作为唯一键。
+   **回调通知器 (Callback Notifier):** 任务完成后，根据请求中提供的回调URL，将结果（或错误信息）通过HTTP POST请求发送给客户端。

#### 3. 核心算法：分层摘要策略

为了避免通用摘要的模板化问题，我们采用“分层摘要”策略，针对不同文件类型和内容结构进行优化。

**阶段一：结构感知的文本提取**

*   **PDF:** 使用 `PyMuPDF` (fitz) 库。提取逻辑：
    1.  识别并提取标题（`/Title` 元数据或最大字号文本）。
    2.  按页面顺序提取文本块，保留段落结构。
    3.  **特殊处理：** 识别并提取表格内容（`find_tables()` 方法），将表格转换为键值对或结构化列表，而不是简单拼接。例如，一个包含“产品”、“数量”、“价格”的表格会被提取为 `[{'产品': 'A', '数量': 10, '价格': 100}, ...]`。
+   **Word (.docx):** 使用 `python-docx` 库。提取逻辑：
    1.  遍历文档的 `paragraphs`，保留标题样式（Heading 1, 2, 3）。
    2.  遍历文档的 `tables`，同样转换为结构化数据。
    3.  提取 `comments` 和 `revisions`（如果存在），作为上下文补充。
-   **Excel (.xlsx):** 使用 `openpyxl` 库。提取逻辑：
    1.  遍历所有工作表（`sheet_names`）。
    2.  对于每个工作表，提取表头行（第一行）作为字段名。
    3.  提取后续数据行，形成列表。**核心摘要点：** 统计行数、识别数值列的汇总（总和、平均值）、发现异常值（如超出3个标准差的数据点）。
+   **图片 (JPG, PNG):** 使用 `Tesseract OCR` 引擎。提取逻辑：
    1.  预处理：灰度化、二值化、降噪。
    2.  OCR识别，获取文本及置信度。
    3.  **过滤低置信度文本：** 丢弃置信度低于0.8的文本片段，避免引入错误信息。

**阶段二：基于LLM的智能摘要**

+   **模型选择：** 使用 `gpt-3.5-turbo-16k` 或 `gpt-4`（根据预算和精度要求）。`16k` 版本可以处理更长的上下文（如大型文档）。
*   **Prompt 工程（核心）：** 采用结构化Prompt，避免让模型自由发挥。

    ```
    System: 你是一个专业的文档摘要助手。你的任务是分析提供的文本，并生成一个结构化摘要。摘要必须包含以下部分：
    1.  **核心主题 (Core Topic):** 用一句话概括文档的核心内容。
    2.  **关键事实与数据 (Key Facts & Data):** 列出文档中提到的具体数字、日期、名称、百分比等。使用项目符号列表。
    3.  **行动项 (Action Items):** 如果文档包含待办事项、建议或要求，请提取出来。使用项目符号列表。
    4.  **结论/建议 (Conclusion/Recommendation):** 文档的最终结论或提出的建议。如果未明确给出，则基于内容进行推断，并标注“推断”。
    5.  **局限性 (Limitations):** 指出文档中可能存在的模糊、矛盾或未提及的重要信息。

    User: 请分析以下从[文件类型]中提取的文本：[提取出的结构化文本]
    ```

+   **示例：** 假设提取自一份PDF销售报告。

    **用户输入（结构化文本）：**
    ```
    文件类型：PDF销售报告
    标题：2023年Q3销售业绩分析
    段落1：本季度总销售额为$1,200,000，同比增长15%。主要增长来自北美市场，贡献了$600,000。
    表格：[{'产品线': 'A系列', 'Q3销售额': '$500,000', '环比增长': '5%'}, {'产品线': 'B系列', 'Q3销售额': '$700,000', '环比增长': '20%'}]
    段落2：B系列的增长主要得益于新发布的B-Pro型号。预计Q4将推出C系列。
    ```

    **模型输出（结构化摘要）：**
    ```
    1.  **核心主题:** 2023年Q3销售业绩报告，显示整体增长，B系列产品表现突出。
    2.  **关键事实与数据:**
        *   总销售额：$1,200,000，同比增长15%。
        *   北美市场贡献：$600,000。
        *   A系列销售额：$500,000，环比增长5%。
        *   B系列销售额：$700,000，环比增长20%。
    3.  **行动项:**
        *   计划在Q4推出C系列产品。
    4.  **结论/建议:**
        *   应继续加大对B系列（特别是B-Pro型号）的投入。
        *   需分析A系列增长放缓的原因。
    5.  **局限性:**
        *   报告未提供各市场（除北美外）的详细数据。
        *   未提及Q4的销售目标。
    ```

#### 4. API 接口定义

*   **POST `/v1/summarize`**
    *   **请求体 (JSON):**
        ```json
        {
          "file_url": "https://example.com/report.pdf", 
          "file_content": "base64_encoded_string", // 与 file_url 二选一
          "file_name": "Q3_Report.pdf", 
          "callback_url": "https://myapp.com/callback", 
          "options": {
            "max_summary_length": 200, // 可选，控制摘要长度
            "focus_on": "numbers" // 可选，让模型重点关注数字
          }
        }
        ```
    *   **响应 (JSON):**
        ```json5
        {
          "task_id": "uuid-string",
          "status": "processing",
          "estimated_time_seconds": 15
        }
        ```

-   **GET `/v1/tasks/{task_id}`**
    *   **响应 (JSON):** 返回任务状态和结果（如果完成）。

#### 5. 部署与监控

-   **容器化:** 使用 Docker，并为每个工作节点（PDF处理器、OCR处理器）创建独立的Docker镜像，以便根据负载独立扩缩容。
+   **健康检查:** 暴露 `/health` 端点，返回服务状态和依赖项（数据库、队列）的连接状态。
-   **监控指标:**
    *   `summary_requests_total`: 总请求数。
    *   `summary_processing_duration_seconds`: 处理耗时直方图。
    *   `summary_file_size_bytes`: 文件大小分布。
    *   `summary_error_total`: 按错误类型（解析失败、OCR失败、LLM超时）分类的错误计数。
    *   `queue_depth`: 任务队列深度。

#### 6. 错误处理与异常情况

-   **文件无法访问:** 返回 `400 Bad Request`，错误信息 `file_unreachable`。
*   **文件格式不支持:** 返回 `415 Unsupported Media Type`。
*   **OCR失败（图片模糊）:** 在摘要中明确标注 `[OCR失败：图片质量过低，无法提取有效文字]`，而不是返回空结果或错误。
*   **LLM API超时:** 重试2次，间隔指数退避（1秒、2秒）。如果仍失败，返回 `503 Service Unavailable`，并记录日志。
+   **摘要长度超过限制:** 如果模型输出过长，服务端进行截断，并在摘要末尾添加 `[...摘要已截断]` 标记。
